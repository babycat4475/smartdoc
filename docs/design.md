# SmartDoc 设计文档

## 1. 问题定义

把非结构化文档文本转成结构化数据，是两个真实场景的公共子问题：

1. **标准制定流程**（中科易德实习场景）：从标准文本抽取字段供下游使用；
2. **文件自动整理**（个人工具场景）：按文档类别归档下载目录。

SmartDoc 把它做成一个可独立部署的 HTTP 服务：`text → {category, fields}`。

## 2. 关键设计决策

### 2.1 为什么是"契约先行"（contracts.py）

每个类别的字段集合、类型、含义在 `FIELD_SPECS` 中显式声明，同一份契约同时用于：

- 生成 LLM 提示词中的 JSON Schema（约束输出）；
- 响应后校验与类型强制转换（`_coerce`：金额字符串→float，列表去噪）；
- 计算 `missing_fields`（找不到的字段填 null 并显式列出，**不允许编造**）。

这使 LLM 输出从"自由文本"变成"可校验的数据接口"，是结构化生成智能体的核心工程手段。

### 2.2 为什么要规则引擎兜底

LLM 有三个不可回避的问题：要钱、会挂、慢。设计为：

```
cache hit → 0ms 返回
LLM 可用 → JSON-mode + 重试(2次, 指数退避) + Schema 校验
LLM 失败/未配置 → 规则引擎（关键词加权 + 结构信号 + 正则抽取）
```

任何情况下服务都返回 200 和合法结构，`engine` 字段告知调用方结果来源。
`/health` 在无 key 时报 `degraded` 而不是假装健康。

### 2.3 缓存设计

`SHA-256(model + category + text)` 作为键。命中即 0ms 返回且落一条 `cache_hit`
事件。对"同一批文档反复调试提示词"的真实工作流，缓存直接把成本和延迟打掉。

### 2.4 存储

stdlib sqlite3（无 ORM 依赖），三张表：documents / cache / events。
写操作加线程锁；连接 `check_same_thread=False` 配合 FastAPI 线程池。
生产可平替 PostgreSQL——Store 是唯一触库层。

## 3. 评测方法论（诚实报告）

三个数据集，角色不同：

| 集合 | 角色 | 规则引擎 | LLM（deepseek-chat） |
|---|---|---|---|
| corpus 46 篇 | 开发集，参与关键词调优 | 100%（有偏，仅回归用） | 100% |
| holdout 26 篇 | 噪声/中英混排，第一轮迭代后验证 | 76.9% → 100%（一轮迭代） | — |
| adversarial 12 篇 | 完全未参与调优 | 75%（3 个失败如实保留） | **100%** |

字段填充率：规则 85.5% vs LLM 96.8%；延迟：规则 ~0.06ms/篇 vs LLM ~967ms/篇。
结论：规则引擎在规范文本上接近完美，在口语化/间接表达上有明确边界；
LLM 把对抗集失败的 3 篇全部救回，定量证明了双引擎设计的价值，
而不是拿开发集 100% 自欺。

## 4. 测试策略

- **单元**：规则引擎分类/抽取/边界（千分位金额、缺失字段、文件名提示）
- **集成**：TestClient 全 API 路径，含 GB18030 编码上传、422/404、OpenAPI 完整性
- **LLM mock**：httpx.MockTransport 模拟 429→重试→成功、非法类别拒绝、围栏 JSON 容错、类型转换
- **服务级**：LLM 抛错→降级 rules；同文二次请求→cache 命中 0ms
- **回归门禁**：开发集准确率 <85% 直接挂测试，防止后续改动悄悄劣化

## 5. 已知局限

- 仅支持纯文本输入；PDF/OCR 在 roadmap
- 规则引擎对间接表达（"温馨提示"式通知）覆盖不足
- 单进程 SQLite，不适合多副本横向扩展（需换 PG + 分布式缓存）
- LLM 字段级置信度未实现，当前只有分类置信度
